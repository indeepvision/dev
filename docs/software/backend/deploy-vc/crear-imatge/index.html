Crear la imatge

Requisits​

  • WSL amb Docker instal·lat. Els scripts criden el Docker des de dins de WSL, perquè la imatge és de Linux. A les imatges de WSL que compartim (i importem per no haver-les de configurar) cal afegir l'usuari al grup docker un sol cop, veure permisos per fer servir Docker.
  • Correr els scripts amb Node.js amb la versió correcta que estiguem utilitzant, la mateixa versió que fixa el Dockerfile. Veure entorn Typescript.
  • El CHANGELOG.md ha de tenir una secció amb la versió del package.json de l'arrel. Els scripts ho comproven abans de fer res.

Preparar el contingut de la imatge​

Important: Executar primer la tasca NX de clean per esborrar el contingut de dist:

npx nx run @indeepvision/visioncloud:clean

Després executar la tasca NX de package:

npx nx run @indeepvision/visioncloud:package
caution

Fer servir la tasca NX i no npm run package. El target de NX declara dependsOn: ["^package", "build", "buildcpp"], i per tant compila primer el VisionCloud i les llibreries internes de les quals depèn. Cridant l'script directament es faria servir el que hi hagi a dist d'una execució anterior, que pot ser antic.

El resultat és la carpeta dist/packages/visioncloud, que és el que Docker llegirà:

  • L'aplicació compilada.
  • El package.json amb les versions exactes i el package-lock.json que li correspon.
  • La carpeta internal-libraries/ amb les llibreries @indeepvision.
  • Els .so i .node dels addons natius, a l'arrel de la carpeta.
  • El .dockerignore, que ha d'estar a l'arrel del context per fer efecte.
caution

No es comprova que no hi hagi cap altre imatge al Docker local de WSL publicada amb la mateixa versió. Si s'afegeix una versió amb el mateix tag (versió) en el registry de Docker local a WSL queda substituïda l'anterior. Això no passa amb el registry d'AWS, que no permet pujar una imatge amb un tag ja existent.

Dependències: què s'instal·la i què es copia​

Aquesta és la part menys evident del disseny, i la raó és diferent per cada tipus de dependència.

Les dependències de tercers s'instal·len dins de la imatge​

El Dockerfile fa npm ci dins del contenidor. No es copien mai les de l'ordinador.

El motiu de no copiar directament la carpeta node_modules a /dist/packages/visioncloud és que alguns packages de Node.js porten binaris compilats per plataforma. Un node_modules instal·lat a Windows conté binaris de Windows, i el contenidor és Linux: fallarien en fer el require(). Instal·lant-les dins de la imatge es compilen o es descarreguen per Linux. Això ho podem fer a Windows, però no a Linux.

Les llibreries internes es copien com a carpetes​

Les llibreries @indeepvision no es poden instal·lar des d'un registry NPM: són packages del monorepo. L'script les copia a internal-libraries/@indeepvision/ i el Dockerfile les mou a node_modules després del npm ci.

L'ordre és important: npm ci esborra el node_modules sencer abans d'instal·lar. Si les llibreries es posessin al node_modules durant el package, l'npm ci de la imatge les eliminaria.

Les versions es resolen del lockfile del monorepo​

El package.json del VisionCloud declara totes les dependències com a "*", i el de l'arrel del monorepo només té rangs (^3.348.0). Cap dels dos diu quina versió s'acaba executant.

L'script agafa la versió exacta del package-lock.json del monorepo, que és la que està realment instal·lada i amb la qual s'ha provat el codi, i genera un package-lock.json nou que correspon a aquest package.json. Així l'npm ci de la imatge és reproduïble.

danger

Si s'instal·len packages de NPM pel VisionCloud i són necessaris en producció (no són dev-dependencies), cal afegir-los al package.json del VisionCloud amb un asterisc "*" enlloc de la versió. L'script els afegirà al package-lock.json amb la versió exacta que hi ha al monorepo. Si no s'afegeixen, l'script els ignorarà i no es podran fer servir dins de la imatge, la imatge fallarà en executar-se.

No cal afegir les devDependencies al package.json del VisionCloud: l'script les ignora i no es copien a la imatge, que només necessita les dependències de producció.

Crear la imatge​

npx nx run @indeepvision/visioncloud:createimg

Genera dues etiquetes sobre la mateixa imatge: una amb la versió, per llegir-la, i una amb el commit de GitHub (per exemple sha-ed20f1ebfb), per poder-la traçar.

visioncloud:11.7.19
visioncloud:sha-ed20f1ebfb
tip

Per saber de quin commit s'ha construït una imatge:

docker inspect visioncloud:11.7.19 --format "{{index .Config.Labels \"org.opencontainers.image.revision\"}}"

Si hi ha canvis sense commitejar, l'script avisa: el commit que queda guardat a la imatge no descriu tot el que hi ha dins. Per publicar-la, en canvi, no s'admet (veure publicar la imatge).
