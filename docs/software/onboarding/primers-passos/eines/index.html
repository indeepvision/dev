Eines

El monorepo s'organitza amb Nx i workspaces de npm: cada projecte és un package dins de packages/. Les tasques habituals (compilar, testejar, empaquetar, publicar…) es fan sempre amb el mateix conjunt d'eines compartides situades a la carpeta tools/ de l'arrel del repositori, que cada package invoca a través dels seus propis scripts.

Aquesta secció n'és una visió general: què hi ha disponible i com fer-ho servir. No pretén documentar cada funció, sinó donar el mapa per situar-se.

Com estan connectades les eines​

No hi ha fitxers project.json per package: Nx dedueix cada projecte del seu package.json, i cada target de Nx correspon a un script de package.json. Aquests scripts són sempre una capa fina que executa un fitxer TypeScript de la carpeta tools/ del package, el qual al seu torn importa la caixa d'eines compartida de l'arrel:

target de Nx  →  script de package.json  →  npx ts-node ./tools/<script>.ts  →  tools/*.ts (arrel)

Per tant, es pot llançar qualsevol tasca de dues maneres equivalents:

# Amb Nx, des de l'arrel del repositori
npx nx run <package>:<target>
npx nx run-many -t build          # executa el target a tots els projectes

# Amb npm, des de dins de la carpeta del package
npm run <script>

Targets habituals​

Gairebé tots els packages comparteixen aquest conjunt de targets:

TargetQuè fa
cleanEsborra la carpeta de sortida dist del package.
buildCompila el codi font (TypeScript, i quan cal Sass/webpack) cap a dist i hi copia els fitxers necessaris.
buildcppCompila el codi C++ amb CMake (només als packages amb addon natiu).
testExecuta els tests compilats del package.
packageConverteix dist en un package llest per publicar: neteja fitxers de desenvolupament i ajusta el package.json.
releasePublica el package al registre privat (amb comprovacions de git i CHANGELOG prèvies).
watch-tsCompilació incremental de TypeScript (tsc --watch) per a desenvolupament.

Els packages de frontend afegeixen variants build-sass / watch-sass i build-webpack / watch-webpack, i sovint generate-svg per generar components a partir d'SVG.

Aquests targets estan encadenats: build → package → release depenen l'un de l'altre, de manera que llançar release executa automàticament els passos previs.

La caixa d'eines compartida (tools/)​

Els mòduls de l'arrel tools/ contenen tota la lògica reutilitzable. Els scripts de cada package només els criden:

  • common-tools.ts — base que fan servir tots els altres: logger amb l'estil d'ID Vision, utilitats de fitxers i carpetes, compressió 7z, conversió de rutes Windows ↔ WSL, execució de comandes npm/npx, gestió de versions i lectura del token de GitHub des del .npmrc.
  • build-tools.ts — compilació: TypeScript, Sass, webpack i CMake (Windows via Visual Studio Developer Command Prompt, Linux via WSL), més còpia de binaris natius i construcció d'imatges Docker.
  • package-tools.ts — preparació per publicar: resol les dependències contra el package.json de l'arrel (política de versió única per a @indeepvision/*), ajusta el package.json del package i neteja els binaris de símbols de depuració.
  • release-tools.ts — publicació: npm publish al registre privat i comprovacions prèvies (branca master, sense canvis sense commitejar, tag de git i entrada al CHANGELOG), més creació de releases a GitHub amb el CLI gh.
  • test-tools.ts — execució de tests de Node, de C++ (natiu o via WSL) i informes de cobertura.
  • ec2-tools.ts — control d'instàncies AWS EC2 (arrencar, aturar, estat), utilitzat pel desplegament de VisionCloud.
  • prompt-tools.ts — prompts interactius de terminal (confirmacions, tria d'opcions) per a les tasques que no accepten arguments per línia de comandes.

Eines específiques d'alguns packages​

Més enllà del conjunt comú, alguns packages tenen tasques pròpies:

  • Packages C++ (vision-elements, visionnode, onevision, brain-server, cam-module, comm-module, compiler-module, indeep-utils, josephine2…) — target buildcpp i, en alguns, testcpp per als tests natius. Requereixen l'entorn C++ configurat.
  • onevision (aplicació Electron d'escriptori) — a més de build/package, té bundle i createinst per generar l'instal·lador MSI de Windows.
  • visioncloud / visioncloud-new / visionnode (serveis cloud) — createimg i runimg per construir i executar imatges Docker, migrate i seed per a la base de dades, i deploy (només visioncloud) per gestionar el desplegament a AWS de manera interactiva.
  • Llocs de documentació (idvision-docs, onevision-docs, visioncloud-docs) — basats en Docusaurus: start per al servidor de desenvolupament i serve/build per a producció.
  • Utilitats de generació de codi — id-styles (generate-colors, generate-fonts), indeep-parameters (generate-parameters) i tf-to-onnx (CLI de conversió de models).

Requisits previs​

Segons la tasca que es vulgui executar, cal tenir configurat:

  • .npmrc amb un token de GitHub — imprescindible per instal·lar i publicar els packages privats @indeepvision/*. Es pot partir de la plantilla tools/example.npmrc:

    @indeepvision:registry=https://npm.pkg.github.com/IndeepVision
    //npm.pkg.github.com/:_authToken=EL_TEU_TOKEN

    Genera el token a Settings → Developer Settings → Personal access tokens amb els permisos workflow, write:packages i delete:packages. El prefix @indeepvision: és necessari perquè només els packages d'ID Vision es baixin del registre privat i la resta se segueixin baixant de npmjs.org.

    danger

    Els packages són privats. No els publiquis mai al registre públic de npm.

  • Entorn C++ (VS Developer Command Prompt + CMake + Ninja al PATH) — per als targets buildcpp. Consulta l'entorn C++.

  • WSL — per a totes les operacions amb destí Linux: compilació C++ de Linux, neteja de binaris, tests de C++, cobertura i construcció d'imatges Docker.

  • AWS CLI i CLI gh — per al desplegament de VisionCloud i per crear releases a GitHub, respectivament.

Esborrar un package publicat a GitHub​

A la secció Packages del repositori, entra a Package settings → Manage versions i esborra la versió concreta. El tag local s'ha d'esborrar manualment amb git tag -d <nom-del-tag>.
